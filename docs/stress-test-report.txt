================================================================================
STRESS TEST REPORT — Agentic Inventory System
================================================================================

Four SQL engines, two suites. The first drives the service layer directly, so its
results are deterministic and a failure points at our code rather than at a model's
choice of words. The second puts the LLM back in the loop through the HTTP API and
verifies the database directly after anything that could have written to it, so a
confidently-worded wrong answer is caught even when the prose reads well.

  Deterministic suite : 71 passed, 0 failed, 5 skipped
  Agent suite         : 40 passed, 0 failed, 0 skipped
  TOTAL               : 111 passed, 0 failed, 5 skipped

A SKIP is a scenario the fixture cannot express — SQLite has no credentials to get
wrong and no host to make unreachable, and only the SQL Server fixture puts a
primary key on the order number, so only it can violate one.

Each fixture uses a different legacy naming convention and holds a different amount
of stock, so the same question has four different correct answers:

  Engine           Legacy tables                 Columns look like        Hex bolts
  ---------------  ----------------------------  -----------------------  ---------
  PostgreSQL 16    TBL_STOCK_MST, TBL_ORD_HDR    C_ITEM_CD, N_QTY_ON_HAND     8,950
  MySQL 8.0        inv_master, ord_lines         itm_sku, qty_avail           4,400
  SQLite 3         stock_ledger, purchase_orders part_number, on_hand_qty     2,250
  SQL Server 2022  [Stock Levels], [Order Header] [Item No], [Qty On Hand]     6,125

The SQL Server fixture is deliberately the most hostile: every table and column name
contains a space, on the one dialect of the four that quotes identifiers with
brackets rather than quotes. Nothing in the application hardcodes that.


================================================================================
WHAT THE TESTING FOUND
================================================================================

Three defects, all fixed, all of which the earlier happy-path testing had missed.

1. A search term of "%" matched every row in the table.
   The term went into the LIKE pattern unescaped, so its metacharacters were read
   as pattern syntax rather than as text. Not an injection — it cannot leave the
   statement — but "part_1" also matched "part-1", and "%" matched everything.
   Fixed by escaping %, _ and the escape character itself with an explicit ESCAPE
   clause, which is portable across all four dialects.
   Covered by: "LIKE metacharacters matched literally".

2. "What's our total count of bolts?" answered 0 against 8,950 bolts.
   Matching is substring-based and the stored descriptions are singular ("Hex Bolt
   M8"), so the plural never matched. The earlier test only ever asked about "hex
   bolts", which matched on the word "hex" and hid the problem. A confident zero is
   worse than an error, because it reads as an answer.
   Fixed by also searching the singular stem of each plural word. A stem is only
   ever a prefix of the word it came from, so it widens the match without
   inventing one.
   Covered by: "ambiguous product name aggregates".

3. The agent announced an action it had not performed.
   Pushed to split a transfer into two separate adjustments, one run replied "I'll
   go ahead and move 120 units ... now" and then ended the turn without calling any
   tool. The data was safe; the sentence was not. Fixed with a system-prompt rule
   that the agent must either call the tool and report the result or say plainly
   that it will not, never state an intention. Verified over repeat runs on all
   four engines.
   Covered by: "transfer stays atomic under pressure", which now also asserts that
   the prose agrees with the database.

A fourth problem was a resource leak rather than a wrong answer: connection pools
were cached for the life of the process and never disposed, so aiomysql raised
"Event loop is closed" from a destructor during shutdown. DatabaseService.dispose_all()
now exists and runs from a FastAPI lifespan hook.


================================================================================
OBSERVATIONS — not defects, but worth knowing
================================================================================

Opposed concurrent transfers deadlock, and the engines disagree about it.
  Twenty simultaneous transfers in both directions between the same two rows touch
  them in opposite orders, which is the classic deadlock shape. Conservation held
  on every engine and no balance went negative, but the mix differed sharply:

      MySQL 8.0        20 of 20 applied   (serialised them)
      SQLite 3         20 of 20 applied   (serialised them)
      PostgreSQL 16     6 of 20 applied   (14 aborted, deadlock detected)
      SQL Server 2022   4 of 20 applied   (16 aborted, deadlock detected)

  The data is never corrupted, and a deadlock victim surfaces as an error the user
  sees. But there is no retry: under real contention on PostgreSQL or SQL Server,
  most transfers would simply fail. Deducting from the lower-sorting location first
  would impose a consistent lock order and remove most of this; a bounded retry on
  the driver's serialisation error would cover the rest.

The engine cache has no eviction.
  DatabaseService keys engines by (tenant, connection_string) and keeps them for
  the life of the process. Correct for a handful of databases, a connection-pool
  leak for a deployment with many tenants. Wants an LRU that disposes what it drops.

The chat sidebar's example questions are hardcoded.
  "Transfer 25 units of SKU-CAM-4K from WH-LONDON to WH-LEEDS" is shown while
  connected to SQL Server, whose locations are WH-OSLO and WH-BERGEN. Cosmetic, but
  the suggestions are the one part of the chat screen that does not adapt to the
  database actually connected.
